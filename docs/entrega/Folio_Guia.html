1. Contexto: ¿qué es Folio?

Un comercio tiene varias cajas registradoras (en la demo, dos: c01 y c02). Cada caja es simplemente un navegador web. Todas envían sus ventas a un computador central, que guarda cada factura completa en una base de datos NoSQL (DynamoDB) y usa Redis como caché para responder más rápido las consultas repetidas.

Dilo así“Folio es un prototipo académico de facturación: varias cajas venden desde el navegador, un servidor central calcula los totales y guarda cada factura en DynamoDB con diseño de tabla única, y Redis acelera las lecturas repetidas sin ser nunca la fuente de verdad.”
Qué hace
  • Ventas desde 2 cajas con carritos independientes.
  • CRUD de productos y clientes (sin borrar).
  • El servidor calcula precios, impuestos y totales.
  • Reintentar una venta no crea facturas duplicadas.
  • Historial por cliente, por caja y por día.
  • Comprobante imprimible.
  • Diagnóstico: de dónde vino el dato (Redis o DynamoDB).
Qué NO hace (alcance académico)
  • No es facturación electrónica DIAN.
  • No hay login ni permisos: el “operador” es un nombre que se escribe.
  • Sin inventario, pagos, devoluciones ni trabajo sin conexión.
  • Las facturas no se editan ni se borran.
  • Datos ficticios, moneda COP.
Objetivos que se pueden verificar
  1. Dos ventas simultáneas desde cajas distintas.
  2. Leer una factura completa sin consultar catálogo ni cliente.
  3. Todos los listados con Query, nunca Scan.
  4. Primera lectura desde DynamoDB, segunda desde Redis.
  5. Una solicitud repetida = una sola factura.
  6. Si Redis cae, se sigue vendiendo.

El proyecto parte del repositorio base del profesor Carlos Oliveros (bd_no_sql), que ya traía Docker + LocalStack + CDK. Folio lo adapta al dominio de facturación y le agrega interfaz, transacciones, idempotencia, historiales y pruebas.

3. Docker: los 3 contenedores (y la web)

El archivo docker-compose.yml define tres servicios. Cada uno tiene un papel distinto. Un cuarto contenedor (frontend, en docker-compose.web.yml) sirve la página web.

Servicio 1

emulador (LocalStack)

Imagen: localstack/localstack:4.14 · Puerto: 4566

Qué es: un “AWS de mentira” corriendo en tu PC. Emula API Gateway, Lambda, DynamoDB, CloudFormation, IAM, S3, etc.

Detalle importante: monta /var/run/docker.sock porque, cuando llega una petición, LocalStack crea contenedores adicionales para ejecutar cada Lambda. Esos contenedores se conectan a la misma red (facturacion_nosql_net) para poder ver a Redis.

Healthcheck: consulta /_localstack/health cada 5 s.

Servicio 2

redis

Imagen: redis:7-alpine

Qué es: la caché en memoria. Se arranca con --appendonly yes (AOF): escribe en disco cada operación, así sobrevive a un reinicio del contenedor.

Guarda datos en el volumen redis_data.

Healthcheck: redis-cli ping → debe responder PONG.

No publica puerto al exterior: solo lo ven las Lambdas dentro de la red Docker (host redis, puerto 6379).

Servicio 3

cdk-dev

Imagen: se construye con el Dockerfile del proyecto.

Qué es: la “caja de herramientas” del desarrollador. Tiene Python 3.11, Node, AWS CDK y cdklocal. Desde aquí se despliega la infraestructura en LocalStack, se cargan datos y se corren las pruebas.

Queda corriendo con sleep infinity para poder entrar con docker compose exec.

Espera (depends_on: service_healthy) a que emulador y redis estén sanos antes de arrancar.

Extra: frontend — usa la misma imagen de cdk-dev, ejecuta serve_frontend.py en el puerto 8080, entrega los archivos de la interfaz y reenvía las llamadas /api al API Gateway de LocalStack. Así el navegador no necesita saber el ID interno de la API.

El Dockerfile: construcción en dos etapas (multi-stage)

# Etapa A: solo se usa para sacar Node
FROM node:24-bookworm-slim AS node_runtime
# Etapa B: la imagen final, basada en Python 3.11
FROM python:3.11-slim-bookworm
COPY --from=node_runtime /usr/local/bin/node ...     # copia Node a la imagen de Python
RUN npm install --global aws-cdk@2 aws-cdk-local     # CDK necesita Node
RUN pip install -r requirements.txt                   # librerías de desarrollo/pruebas
    pip install -r runtime-requirements.txt --target /opt/lambda-deps   # librerías que viajan dentro de cada Lambda (boto3, redis)
CMD ["sleep", "infinity"]

¿Por qué así? CDK es una herramienta de Node, pero el proyecto está en Python. En vez de instalar Node a mano, se toma de una imagen oficial y se copia: la imagen final queda con ambos, más liviana y reproducible. Las dependencias de las Lambdas se dejan preparadas en /opt/lambda-deps y el CDK las mete en el zip de cada función (enfoque del profesor, sin Lambda Layers).

Las 3 fases de arranque (lo que hace Iniciar-Proyecto.ps1)

  1. Construir y levantar: docker compose up construye la imagen de cdk-dev y arranca emulador + redis + cdk-dev, esperando sus healthchecks.
  2. Desplegar: desde cdk-dev se hace cdklocal bootstrap y deploy: CloudFormation crea en LocalStack la tabla con sus GSI, las 3 Lambdas y la API. Luego publicar_api.py publica el stage prod y seed_demo.py carga datos ficticios.
  3. Verificar y servir: corre pruebas, arranca el contenedor frontend en el puerto 8080 y muestra los enlaces de Caja 1 y Caja 2.
Dilo así“Docker Compose levanta tres servicios: LocalStack, que emula AWS; Redis, la caché; y cdk-dev, el entorno con CDK desde el que desplegamos la infraestructura como código. Las Lambdas las ejecuta LocalStack en contenedores propios dentro de la misma red, por eso pueden llegar a Redis.”

4. DynamoDB: Single Table Design

En SQL harías una tabla por entidad y las unirías con JOIN. DynamoDB no tiene JOIN. Por eso se diseña al revés: primero se listan las preguntas que la app va a hacer (patrones de acceso) y después se escogen las claves para que cada pregunta se responda con una sola operación barata.

Todas las entidades viven en una sola tabla llamada Facturacion, con dos claves genéricas de tipo String:

  • PK (Partition Key): decide en qué “grupo” (partición) vive el ítem.
  • SK (Sort Key): distingue y ordena los ítems dentro de ese grupo.
  • PK + SK juntos identifican un ítem de forma única.
EntidadPKSKComentario
ProductoPRODUCTO#<uuid>DATOSTiene version para control de concurrencia.
ClienteCLIENTE#CC#90000001PERFILID canónico tipo#número (string, conserva ceros).
CajaCONFIG#CAJASCAJA#c01Todas las cajas en la misma partición → se listan con un Query.
FacturaFACTURA#<uuid>DOCUMENTODocumento completo, inmutable.
SolicitudSOLICITUD#c01#<uuid>RESULTADOEvita facturas duplicadas al reintentar.

Los prefijos (PRODUCTO#, FACTURA#…) evitan choques entre entidades y hacen legible la tabla. Es un requisito del proyecto final del profesor.

Desnormalización: la factura es una “foto” de la venta

Cada factura copia el nombre del cliente y, por cada línea, el nombre del producto, su versión, precio e impuesto tal como estaban al vender. Si mañana cambia el precio del producto, la factura vieja no cambia. Y para leerla basta un GetItem: no hay que reconstruirla consultando catálogo y cliente.

Fíjate: una misma factura lleva las claves de los 3 índices. DynamoDB la “copia” automáticamente a cada GSI.

Dinero sin errores de redondeo: todo se guarda como enteros en centavos (10000 = $100,00) y el impuesto en puntos básicos (1000 = 10 %). Se calcula con Decimal y redondeo HALF_UP por línea, nunca con float.

5. Patrones de acceso

Un patrón de acceso es una pregunta concreta que la aplicación le hace a la base de datos. En NoSQL se diseñan antes que la tabla. Folio tiene 13:

IDPreguntaOperación en DynamoDBDónde
AP01Dame un producto por su IDGetItem PK=PRODUCTO#P, SK=DATOSTabla + caché
AP02Catálogo paginado por nombreQuery GSI1PK=CATALOGO#PRODUCTOSGSI1
AP03Un cliente por identificaciónGetItem PK=CLIENTE#C, SK=PERFILTabla
AP04Directorio de clientes por nombreQuery GSI1PK=DIRECTORIO#CLIENTESGSI1
AP05Cajas configuradasQuery PK=CONFIG#CAJAS y begins_with(SK,"CAJA#")Tabla

AP08Facturas de la caja T entre dos fechasQuery GSI2PK=CAJA#T y GSI2SK BETWEENGSI2
AP09Facturas del día D del comercioQuery GSI3PK=VENTAS#DIA#DGSI3

Cómo leer esto

GetItem

“Dame exactamente este ítem.” Necesita PK y SK completas. Es la operación más rápida y barata. Se usa para los detalles (AP01, AP03, AP06, AP10).

Query

“Dame todos los ítems de esta partición, opcionalmente filtrando el rango de la SK.” Lee solo lo necesario, ya ordenado por la SK. Se usa para listados.

Scan (prohibido)

Recorre la tabla entera y filtra después. Lento y caro. Ningún flujo de Folio usa Scan: por eso existen los GSI.

Paginación: los listados devuelven máximo 25 ítems y un cursor. Ese cursor es la LastEvaluatedKey de DynamoDB; en la siguiente petición se envía como ExclusiveStartKey. El servidor valida que el cursor corresponda a la misma consulta y filtros (no se puede “reutilizar” un cursor de otra búsqueda).

Dilo así“En NoSQL el modelo nace de las preguntas. Definimos 13 patrones de acceso y cada uno se resuelve con un GetItem, un Query o una transacción. Los detalles usan la clave primaria; los listados usan índices secundarios globales. No hay ningún Scan.”

6. Los 3 índices secundarios globales (GSI)

La tabla principal solo sabe buscar por PK. Pero las facturas tienen PK = FACTURA#uuid: con eso no se puede preguntar “¿qué compró el cliente X?”. Un GSI es otra “vista” de la misma tabla con otra clave de partición y otra clave de ordenamiento. DynamoDB lo mantiene actualizado solo.

Los tres GSI funcionando en la plataforma

La pantalla Historial tiene un selector “Consultar por” con tres opciones. Cada opción corresponde a un GSI:

Las columnas del listado (referencia, fecha, cliente, caja y total) son justamente los atributos proyectados con INCLUDE. Las líneas de la factura no están en el índice: aparecen solo al pulsar “Ver comprobante”, que hace un GetItem a la tabla.

¿Por qué estos y no otros? Las decisiones, una por una

¿Por qué tres GSI y no uno solo?

Porque son tres preguntas con tres “dueños” distintos de la partición: el cliente, la caja y el día. Un ítem puede aportar solo una pareja de claves por índice. Una factura necesita aparecer a la vez en la partición de su cliente, de su caja y de su día; con un solo índice tendrías que duplicar la factura en ítems de relación adicionales. Con tres índices, la misma factura aparece en los tres lugares sin escribir nada extra.

¿Por qué GSI1 está “sobrecargado” (mezcla productos, clientes y facturas)?

La sobrecarga de índices es una técnica de Single Table Design: como las claves son genéricas (GSI1PK/GSI1SK), entidades diferentes pueden compartir un mismo índice usando prefijos distintos en la partición. CATALOGO#PRODUCTOS, DIRECTORIO#CLIENTES y CLIENTE#… nunca se mezclan en una consulta porque siempre se consulta una partición concreta. Ahorra índices (DynamoDB permite 20 GSI por tabla y cada uno cuesta almacenamiento y escrituras).

¿Por qué la SK es FACTURA#fecha#id?
  • La fecha va primero y en formato UTC de ancho fijo (2026-11-12T03:15:00.000Z). Como son strings, el orden alfabético = orden cronológico. Eso permite BETWEEN :lo AND :hi para pedir un rango de fechas directamente en la clave, sin filtros.
  • El id va al final para desempatar dos ventas en el mismo milisegundo y que cada SK sea única.
  • Se consulta en orden descendente (lo más reciente primero).
  • Los rangos son inicio incluido, fin excluido, y como máximo 31 días.
¿Por qué el día se calcula con hora de Bogotá?

Una venta a las 10:15 p. m. del 11 de noviembre en Colombia es 03:15Z del 12 en UTC. Si agrupáramos por fecha UTC, esa venta caería en el día equivocado. Por eso GSI3PK usa fecha_local (America/Bogota), y la SK sigue en UTC para ordenar.

¿Por qué GSI3 parte por día y no tiene una sola partición “VENTAS”?

Si todas las facturas de la historia fueran a una única partición, sería una partición caliente: crecería sin límite y concentraría todas las escrituras. Partir por día reparte la carga y coincide con la pregunta real (“ventas de hoy”). El catálogo y el directorio sí están en una sola partición, pero porque su volumen es pequeño en el prototipo; el documento de diseño reconoce que habría que dividirlas si creciera.

¿Qué es la proyección INCLUDE y por qué se usó?

Un GSI no copia necesariamente todo el ítem. Se eligió INCLUDE: solo se copian las claves y unos atributos seleccionados.

  • GSI1: tipo_entidad, nombre, activo, version, precio_unitario_centavos, impuesto_bps, factura_id, fecha_utc, caja_id, cliente_id, total_centavos (sirve para catálogo, directorio y resúmenes de factura).
  • GSI2 y GSI3: solo el resumen: factura_id, fecha_utc, caja_id, cliente_id, total_centavos.

Así el listado muestra lo necesario (fecha, caja, cliente, total) y no se duplican las líneas de cada factura en tres índices. Al hacer clic en una, se trae el detalle completo con un GetItem a la tabla (y Redis).

Alternativas descartadas: ALL (copiaría todo el documento 3 veces: más almacenamiento y más costo por escritura) y KEYS_ONLY (obligaría a un GetItem por cada fila del listado).

Índices dispersos (sparse)

Un ítem solo aparece en un GSI si tiene sus atributos de clave. Los productos y clientes no tienen GSI2PK ni GSI3PK, así que GSI2 y GSI3 contienen solo facturas. Las solicitudes no tienen ninguna clave GSI y no aparecen en ningún índice.

Consistencia eventual de los GSI

Los GSI se actualizan de forma asíncrona: una factura recién creada puede tardar un instante en aparecer en el historial. Por eso la interfaz muestra la factura con la respuesta del POST y, cuando se necesita certeza (reintentos, leer el documento recién emitido), se usa lectura fuertemente consistente (ConsistentRead=True) sobre la tabla principal. Los GSI no admiten lectura consistente.

Dilo así“Tenemos tres GSI porque tenemos tres formas de mirar las facturas: por cliente, por caja y por día. GSI1 está sobrecargado y además sirve para el catálogo y el directorio. La clave de orden empieza por la fecha UTC, así que un rango de fechas es un BETWEEN sobre la clave, sin Scan ni filtros. Proyectamos solo un resumen con INCLUDE y el detalle se lee por ID.”

7. ¿Y los LSI?

Importante antes de exponer: este proyecto no tiene ningún LSI. En app/infra/stack.py solo se crean GSI1, GSI2 y GSI3, y la documentación habla de “tres GSI”. No digas que se escogieron LSI. Lo que sí puedes (y deberías) explicar es por qué no se usaron: es una decisión de diseño defendible.

Qué es un LSI

Un Local Secondary Index mantiene la misma clave de partición que la tabla y solo cambia la clave de ordenamiento. Es decir: ordena distinto dentro del mismo grupo, pero no permite agrupar por otro criterio.

GSI (lo que usa Folio)LSI
Clave de particiónDistinta a la de la tablaLa misma que la tabla
Clave de ordenamientoDistintaDistinta
¿Cuándo se crea?En cualquier momentoSolo al crear la tabla; luego no se puede agregar ni quitar
Límite20 por tabla5 por tabla
Lectura consistenteNo (eventual)Sí, admite lectura fuerte
TamañoSin límite por particiónMáx. 10 GB por valor de PK (colección de ítems)

Por qué un LSI no sirve aquí

  1. Las preguntas necesitan otra partición. La factura tiene PK = FACTURA#uuid, y cada partición contiene una sola factura. Un LSI solo podría reordenar los ítems de esa partición… que es uno. No sirve para “todas las facturas del cliente C” ni “de la caja T” ni “del día D”: eso exige agrupar por cliente, caja o día, es decir, cambiar la clave de partición → GSI.
  2. Rigidez. Un LSI se define al crear la tabla y no se puede añadir después. Los GSI se pueden agregar a medida que aparecen nuevos patrones de acceso.
  3. Límite de 10 GB por valor de partición en tablas con LSI, que limitaría el crecimiento.
  4. La ventaja del LSI (lectura fuertemente consistente) ya se cubre de otra forma: las lecturas críticas (detalle de factura, solicitud de reintento) van a la tabla principal con ConsistentRead=True.
¿Cuándo SÍ tendría sentido un LSI? (por si lo preguntan)

Si se hubiera modelado “cliente” como partición (PK=CLIENTE#C) con sus facturas dentro (SK=FACTURA#fecha#id), un LSI podría ordenar esas mismas facturas por total (“las compras más grandes del cliente”). Pero en Folio esa pregunta no existe, y ese modelo solo cubriría el historial por cliente: seguiría necesitando GSI para caja y día.

Dilo así“No usamos LSI a propósito. Un LSI comparte la clave de partición de la tabla, y nuestra partición de factura es la propia factura. Nuestras consultas agrupan por cliente, por caja y por día, o sea, necesitan otra clave de partición, y eso solo lo da un GSI. Además los LSI se fijan al crear la tabla y limitan a 10 GB por partición. La lectura consistente la resolvemos leyendo la tabla principal.”

8. Cómo funciona Redis en este proyecto

Redis es una base de datos en memoria (clave → valor), muy rápida. Aquí no es la fuente de verdad: es una copia temporal. Si se pierde todo lo que hay en Redis, no se pierde ningún dato.

Patrón Cache-Aside (“caché a un lado”)

La aplicación (no Redis) decide cuándo leer y cuándo llenar la caché:

1. Llega GET /productos/{id}
↓ ¿está en Redis?
HIT ✓devolver la copia de Redis
X-Data-Source: redis
MISS ✗leer DynamoDB → guardar en Redis con TTL (SET … EX) → devolver
X-Data-Source: dynamodb

El código está en app/lambdas/cache_layer.py (clase CachedReads.load).

Qué se cachea y por cuánto tiempo

DatoClave en RedisTTL¿Por qué ese TTL?
Detalle de productofacturacion:v1:producto:<uuid>60 sEl precio puede cambiar; TTL corto limita cuánto tiempo puede verse un dato viejo. Además se invalida (DEL) al actualizar el producto.
Facturafacturacion:v1:factura:<uuid>300 sLa factura es inmutable: nunca queda desactualizada, así que puede vivir más. Solo expira para no llenar la memoria.

El v1 en la clave es la versión del esquema: si el formato cambia, se usa v2 y las copias viejas simplemente se ignoran.

Qué NO se cachea (y por qué)

  • Crear una venta: los precios se verifican siempre en DynamoDB. La caché nunca decide cuánto se cobra.
  • Listados e historiales: cada venta o edición cambiaría muchas listas; habría que invalidar demasiadas claves. No vale la pena.
  • Clientes y cajas: menos frecuentes; se leen directo.
  • Los 404: si algo no existe, no se guarda en caché.

Invalidación al actualizar un producto

  1. Se guarda el cambio en DynamoDB con condición de versión.
  2. Después se borra la clave de Redis (DEL).
  3. La próxima lectura es un miss → trae la versión nueva.

Se reconoce una pequeña ventana: una lectura concurrente podría volver a guardar la versión vieja; el TTL de 60 s la acota. Y como el cobro se valida en DynamoDB, eso nunca afecta el dinero.

Si Redis falla, el sistema sigue

  • Timeout máximo de 200 ms por conexión y lectura, sin reintentos automáticos.
  • Si Redis no responde, hay JSON corrupto, una clave sin TTL o datos incoherentes → se trata como miss y se lee DynamoDB.
  • Antes de devolver una copia de Redis, se valida el documento (esquema, ID, que los totales cuadren). Una copia inválida se borra.
  • Las ventas no dependen de Redis: si está caído, se siguen registrando.

Redis corre con AOF (--appendonly yes), así que su contenido sobrevive a reinicios del contenedor; aun así, perderlo no tendría consecuencias.

Dilo así“Usamos Cache-Aside: primero Redis; si no está, DynamoDB y guardamos la copia con TTL. Productos 60 segundos porque su precio cambia y además los invalidamos al editarlos; facturas 300 porque son inmutables. Redis es opcional: si cae, todo lee de DynamoDB y se sigue vendiendo. Y la venta nunca usa la caché para el precio.”

9. Cómo se registra una venta (idempotencia y transacción)

El reto: si la red falla después de enviar la venta, el cajero no sabe si se guardó. Si reintenta, ¿se duplica la factura? Folio lo evita con idempotencia (repetir la misma operación da el mismo resultado).

  1. El navegador genera un UUID de solicitud y guarda la venta pendiente antes de enviarla.
  2. El servidor calcula un hash SHA-256 de la intención (caja, cliente, líneas).
  3. Lee SOLICITUD#caja#uuid con lectura consistente. Si existe con el mismo hash → devuelve la factura original (200, replayed: true). Si el hash es distinto → 409.
  4. Si es nueva: lee productos, cliente y caja directo de DynamoDB (sin caché) y compara versiones. Si el precio cambió → 409 y el cajero reconfirma.
  5. Calcula los totales en el servidor (el cliente nunca impone el total).
  6. Ejecuta TransactWriteItems: Put de la factura + Put de la solicitud (ambos con attribute_not_exists) + ConditionCheck de la versión de cada producto, del cliente y de la caja activa. O se guarda todo o nada.
  7. Responde 201 con la factura.

Máximo 50 productos + cliente + caja + 2 Put = 54 acciones, dentro del límite de 100 de DynamoDB.

Control de concurrencia optimista: productos y clientes tienen un campo version. Una actualización solo se aplica si la versión esperada coincide (UpdateItem condicional), y luego se incrementa. Así dos personas no se pisan los cambios.

10. Guion sugerido para la demo

  1. Mostrar el estado de servicios (GET /health: DynamoDB, Redis y los 3 GSI).
  2. Abrir Caja 1 y Caja 2 en dos ventanas; escribir un operador.
  3. Consultar un producto dos veces: la 1.ª dice dynamodb / miss, la 2.ª redis / hit.
  4. Hacer una venta en cada caja y abrir los comprobantes.
  5. Reenviar la misma venta → devuelve la misma factura, no crea otra.
  6. Cambiar el precio de un producto → la factura anterior conserva su precio original.
  7. Consultar historial por cliente (GSI1), por caja (GSI2) y por día (GSI3).
  8. Detener Redis (docker compose stop redis) y vender: funciona igual. Volver a iniciarlo.
  9. Mostrar las pruebas: docker compose exec -T cdk-dev python -m pytest tests -q.

11. Preguntas probables y respuestas cortas

¿Por qué NoSQL y no una base relacional?

Porque el acceso es predecible (13 patrones) y la factura es un documento que se escribe una vez y se lee completo. DynamoDB lo resuelve con GetItem/Query de latencia constante, sin JOIN. Es además el objetivo de la materia.

¿Por qué una sola tabla?

Requisito del proyecto y práctica recomendada en DynamoDB: entidades distintas comparten claves genéricas (PK/SK, GSIxPK/GSIxSK) y se distinguen por prefijos. Menos tablas que administrar y los índices se reutilizan (sobrecarga de GSI1).

¿No es malo duplicar datos del cliente y productos en la factura?

Es desnormalización deliberada: la factura debe reflejar cómo fue la venta. Si el precio cambia después, la factura vieja no debe cambiar. Y se lee con un solo GetItem.

¿Cómo evitan facturas duplicadas?

Registro de solicitud con UUID + hash de la intención, guardado en la misma transacción que la factura. Un reintento encuentra la solicitud y devuelve la factura original.

¿Qué pasa si dos cajas venden al mismo tiempo?

Cada venta tiene su propio UUID de factura y de solicitud; no compiten por la misma clave. No hay contador central de consecutivo, así que no hay cuello de botella.

¿Qué pasa si cambia un precio mientras se está vendiendo?

La transacción incluye ConditionCheck sobre la versión del producto; si cambió entre la lectura y la escritura, la transacción entera se rechaza y no queda venta parcial.

¿Por qué no cachean los historiales?

Cada venta cambiaría varias listas (cliente, caja, día). Invalidar todo eso añade complejidad y riesgo de mostrar datos viejos. Los historiales ya son eficientes por los GSI.

¿Por qué LocalStack y no AWS real?

Para no requerir cuenta ni pagar, y que cualquiera pueda clonar el repo y levantar todo con Docker. Es el entorno del proyecto base del profesor.

¿Qué es CDK?

Infraestructura como código: en vez de crear la tabla e índices a mano en la consola, se describen en Python (stack.py) y CDK genera una plantilla de CloudFormation y la despliega. Es reproducible.

¿Por qué el dinero en centavos?

Los float tienen errores de redondeo (0.1 + 0.2 ≠ 0.3). Con enteros en centavos y Decimal con HALF_UP los totales son exactos.

¿Limitaciones?

El equipo central es un punto único de fallo; catálogo y directorio están en una sola partición (bien para el volumen del prototipo); no hay autenticación; no es facturación fiscal.
